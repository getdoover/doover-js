Implementation and follow-up plan

A smaller doover-js.

Publish native ES modules so bundlers can remove unused features. Add focused entry points for smaller consumers. Keep the existing root API and CommonJS support.

The packaging change removes the largest obstacle first. Applications that use DooverClient still retain its full set of services; further reductions need changes to how those services are composed.

02

Implemented in this change

Implemented

Native ESM and CommonJS

import resolves to dist/esm. require keeps the CommonJS build in dist. Each format receives matching declaration files. Existing root exports remain available.

Implemented

Removable unused modules

sideEffects: false allows bundlers to discard unused modules. The source audit found no import-time network requests, filesystem access, timers, or event listeners.

Implemented

Focused entry points

Individual APIs, clients, auth, HTTP, gateway, utilities, and public React hooks have supported package paths. Consumers can choose the parts they need without importing the full convenience client.

Implemented

Clean production output

The build clears stale output and excludes src/test. Package checks exercise the built exports and consumer bundles. npm run size writes a reproducible size report.

Compatibility boundaries. The module export condition directs supporting bundlers to one ESM copy even when dependencies mix import and require. Native Node.js, and bundlers that disable this condition, can load both builds. Those builds have separate class identities and React contexts. Use one format in each runtime so providers, hooks, and instanceof checks agree. Shared singleton helpers use global keys, but other module state is not shared.

The native ESM build exposes named exports. Replace an implicit CommonJS default import with named imports or import * as doover from "doover-js". Root CommonJS consumers keep working and still load the broad root graph. Focused CommonJS entry points reduce what gets loaded. Browser bundlers must resolve the ESM build and enable tree shaking to get the measured reductions.

03

Choose imports by the work you need

Named imports from doover-js now support tree shaking. Smaller package paths also make dependencies explicit and help CommonJS consumers avoid the root graph.

A utility or a single REST API

import { extractSnowflakeId } from "doover-js/utils";
import { RestClient } from "doover-js/http";
import { ChannelsApi } from "doover-js/apis/channels";
import type { Channel } from "doover-js/types";

// Use your existing configuration and explicit auth instance.
const channels = new ChannelsApi(new RestClient(config, auth));

The measured 5,236-byte composition includes RestClient and ChannelsApi, with ambient cookies and no separate auth class. Explicit token auth or cookie refresh adds its chosen auth implementation. Low-level APIs return server data directly; they do not provide the provenance, status, or capability behaviour of DooverClient.

Optional clients and React hooks

import { getDooverClient } from "doover-js/client";
const cloud = getDooverClient(config);
import { LocalAgentClient } from "doover-js/local";
import { MultiplexClient } from "doover-js/multiplex";
import { OfflineDataClient } from "doover-js/offline";

import { DooverProvider } from "doover-js/react/context";
import { useClientStatus } from "doover-js/react/useClientStatus";

The cloud entry exports getDooverClient and shares the root singleton. Its startup bundle excludes offline, local-device, multiplex, and React implementations. Choose the client imports your application uses. The context and status hook need React; query hooks additionally need React Query. Importing DooverClient from /client still includes all services that its constructor creates.

04

The next reductions need composition

DooverClient creates every API, both transport services, the viewer adapter, and diagnostics. Tree shaking cannot discard code that a retained constructor uses. These proposals are future work.

  1. P1

    Offer an opt-in composed client

    Provide a documented way to assemble an HTTP client with selected API factories and an explicit auth implementation. Keep DooverClient as the convenience API.

    Expected benefit
    REST applications can omit gateway, RPC, viewer, unused APIs, and unused auth modes. Exact savings need a working composition prototype.
    Compatibility
    Additive if the current constructor and DataClient contract stay intact. Synchronous lazy getters alone do not remove static imports.
    Acceptance
    A channels-only authenticated consumer makes a real request through an injected fetch implementation. Its bundle excludes gateway, RPC, viewer, multiplex, and offline modules.
  2. P2

    Retire the default viewer adapter

    DooverDataProvider is deprecated but still constructed for every cloud client. It also constructs another set of API instances.

    Expected benefit
    The adapter contributes 3,349 minified bytes to the measured cloud fixture. Its removal needs a new whole-bundle measurement to establish gzip savings.
    Compatibility
    Removing client.viewer is breaking. Keep an explicit adapter import and publish a migration before removal.
    Acceptance
    A cloud client bundle excludes the adapter. Existing adapter methods have documented replacements and migration coverage.
  3. P3

    Split only the large features consumers partially use

    Multiplex and offline modules are about 22.5 kB and 17.6 kB independently minified. They already disappear when unused. Further work matters for applications that use only part of either feature.

    Expected benefit
    Optional endpoint functions or feature factories may remove unused methods. Use consumer profiles to choose the first split; source line counts do not predict gzip savings.
    Compatibility
    Additive factories can preserve existing classes. Rewriting routing and offline policies risks behavioural regressions.
    Acceptance
    The selected consumer becomes measurably smaller, with existing routing, caching, and reconnect tests still passing. Revert splits that do not reduce bundles.
  4. P4

    Keep the package small across releases

    Linux package checks now run on pull requests and main. Retain bundle budgets and track the archive separately. Review new top-level code before keeping sideEffects: false.

    Expected benefit
    Prevent a future barrel, dependency, or stale test build from undoing the current reductions. This prevents growth rather than promising another percentage reduction.
    Compatibility
    No runtime API change. Budget changes need a recorded reason when new functionality raises the baseline.
    Acceptance
    CI rejects wrong export targets, missing declarations, bundled optional peers in core fixtures, compiled tests, and unexpected size increases.

Low-value targets. Core has no regular runtime dependencies to replace. OpenAPI types erase during compilation and are not browser runtime weight. The refine adapter has no runtime import of @refinedev/core. Removing optional peer metadata would not itself reduce its JavaScript bundle.

05

Reproduce and review the evidence

Run these commands from the repository root. The size command rebuilds the package and refreshes the JSON report. This HTML captures the measurements for this change. The size command reports the current build; the optional baseline comparison below reproduces the before-and-after figures.

npm ci
npm test
npm run size
npm pack --dry-run --json

For the historical comparison, build commit 57d6a88 in a separate checkout with its original build configuration. Then pass that checkout to the package checker:

node scripts/check-package.mjs \
	--baseline /path/to/built-baseline-checkout \
	--report docs/optimisation-sizes.json

A normal npm run size refreshes current measurements without historical columns. Use --baseline to regenerate the before-and-after figures.

Recreate the baseline comparison

Run after npm ci and npm run build. Include the original README and licence so archive sizes compare the complete published packages.

baseline_dir="$(mktemp -d)"
git archive 57d6a88 src tsconfig.json package.json README.md LICENSE | tar -x -C "$baseline_dir"
ln -s "$PWD/node_modules" "$baseline_dir/node_modules"
node node_modules/typescript/bin/tsc -p "$baseline_dir/tsconfig.json"
node scripts/check-package.mjs --baseline "$baseline_dir" --report docs/optimisation-sizes.json

The baseline uses the same installed compiler and bundler as the new build. The report includes both complete package archives and equivalent browser fixtures.

Verified for this change: type checking, 316 source tests, and 53 code entry points loaded through both ESM and CommonJS. Package checks also verify declarations, core imports without optional peers, a channels request, shared root/subpath identities, one context in mixed-format bundles, and bundle exclusions.

The build is defined in scripts/build.mjs. Consumer fixtures and size assertions are in scripts/check-package.mjs. Repeating gzip on the whole application may produce different savings because shared code and compression change the result.
